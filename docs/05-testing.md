# 5. Testing

← [Index](README.md) · Prev: [Implementation Phases](04-implementation-phases.md) · Next: [Deployment](06-deployment.md)

Three layers + manual visual checks. Nothing here needs internet at run
time beyond the initial NuGet/Playwright restores.

## 1. Unit tests — `PrintShelf.Stl` (highest value, write first)

xUnit. The parser is pure and deterministic — golden fixtures live in
`src/tests/PrintShelf.Stl.Tests/fixtures/` (committed, each < 100 KB except one
synthetic 100k-triangle perf fixture, generated by `tools/make_fixtures.py`).

Fixtures to hand-craft (tiny, scripted generation is fine):
- binary cube (12 tris): known bbox 10×10×10 mm, known volume 1000 mm³
- ASCII cube: same values as binary — proves both paths agree
- truncated cube (cut mid-triangle) → specific error, not crash
- header lies about tri-count → rejected
- NaN vertex → rejected
- `solid` string inside a *binary* header (classic false-positive) →
  still detected as binary
- degenerate: 0 triangles; empty file
- inverted-winding cube → volume flagged (negative before abs)

Also unit-test: SHA-256 dedupe decision logic, magic sniff, volume
estimation tolerance (relative error < 1e-6 on the cube).

## 2. Service/integration tests (EF Core)

- Use EF Core with a **real local PostgreSQL test database** (schema-per-run
  or `EnsureCreated` on a scratch DB) — SQLite test doubles hide Npgsql
  type quirks (`citext`, numeric precision).
- Cover: upload transaction order (file-then-row), soft delete, dedupe
  keep-both vs skip, integrity scan finds seeded orphan + dangling row.
- Slicer tests: locator resolves explicit executable paths; launch service
  passes the server-resolved STL to the selected allow-listed app through a
  fake process starter (no GUI launched in tests).

## 3. Component tests — bUnit

- Model list renders seeded rows, search box filters (service mocked).
- Upload page rejects wrong extension client-side before any call.
- Tag chips add/remove round-trip.
- Keep this layer thin — the risky logic is in services, not components.

## 4. E2E — Playwright (C# or Node — pick at P3 gate)

**Chosen: Node Playwright** (`src/tests/e2e`, `@playwright/test` 1.64.1).
Start the app first, then `cd src/tests/e2e && npx playwright test`.

Flows (against the real app + real Postgres + real files):
1. upload cube STL → stats shown → detail page → preview canvas visible
2. duplicate upload → dedupe prompt → skip
3. search "cube" from grid; filter by tag
4. print-run add → aggregate card updates
5. category create/rename/colour → upload into it → preview uses that material colour
6. select two models in the catalogue → bulk-assign them to a category → reload confirms the category persisted
7. CSV export downloads and parses with expected row count

Assertions on the preview: canvas exists, no console errors, and (U-02)
thumb `<img>` has natural size > 0 after first preview. Do **not**
pixel-compare WebGL output generally; the one exception is the category
colour test, which reads the centre pixel to prove the material changed.

## 5. Manual visual checks (every UI phase)

- Tailwind: dark/light surfaces readable at 1280 px and 390 px widths.
- Preview: orbit/zoom smooth on the 100k fixture [NFR-04]; rotate 10 models
  then check browser memory is flat (dispose leak check).
- Upload progress bar tracks bytes, not just indeterminate.
- Slicer card: installed apps are enabled, missing apps are disabled, and the
  Launch button is disabled without a detected app.

## 6. Performance spot-checks (P2/P4)

- Parse 100k-triangle binary STL < 1 s [NFR-04 companion]. ✅ passes the test budget.
- Catalogue query with search+filters < 300 ms on 1 000 seeded rows. ✅
  integration test asserts the median; measured page responses were 19–26 ms.
- Seeding script: `dotnet run -- seed 1000` (fixture generator) — also
  useful for demoing to the user at gates.

Actual measured numbers and the preview/memory check are in
[Build Record §3](08-build-record.md#3-performance-evidence).

## 7. Gate evidence per phase

Each phase's validation gate shows: `dotnet build` result, `dotnet test`
result, E2E run (from P3), and screenshots of the phase's pages. The exact
checklist per phase is `acceptance_checks` in [phase-plan.json](../phase-plan.json).
